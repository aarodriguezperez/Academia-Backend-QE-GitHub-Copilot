Nivel A · Rama 0 · Basic concepts → Tools → Thread Pool

A1 ExecuterService no existe

A1

Una clase que no compila

Cuesta tiempo

Recorte del mapa · rama 0. Basic concepts → Tools → Thread Pool

Dice
ExecuterService
Debe decir
ExecutorService
Por qué importa
Es un nombre de clase, no prosa. Si lo tecleas en Eclipse no compila y el autocompletado no te ayuda, porque esa clase no existe en ninguna versión del JDK. El nombre correcto es java.util.concurrent.ExecutorService — de executor, el que ejecuta.
Verificado
Javadoc de java.util.concurrent. Los otros cuatro nombres del mismo nodo (ForkJoinPool, ConcurrentHashMap, BlockingQueue, CompletableFuture) sí están bien escritos.

Nivel A · Rama 2 · Data only vs 3 Channel

A2 Un flujo que falla y termina bien

Esta es la más seria de todas, porque no es una errata de tecleo: es un dibujo que enseña algo que el propio mapa desmiente dos ramas más allá.

A2

Dos señales terminales en la misma línea

Cuesta tiempo

Recorte del mapa · rama 2. Java Streams vs Reactive Streams → Data only vs 3 Channel

Dice
valores → ✕ error → | completado, todo en una sola línea de tiempo
Debe decir
o termina en ✕, o termina en |, nunca las dos
Por qué importa
El contrato de Reactive Streams es onSubscribe onNext* (onError | onComplete)?. Ese paréntesis con la barra vertical significa “una de las dos, no ambas”, y el signo de interrogación significa “como mucho una vez”. Un flujo que emite onError está muerto: no puede emitir onComplete después, ni ninguna otra cosa. Un alumno que estudie de este dibujo va a razonar mal sobre el manejo de errores.
De dónde sale
El dibujo original es una leyenda de símbolos — enseña qué significan el círculo, la cruz y la barra— no una secuencia válida. Colgado directamente de los nodos Data / Error / Complete y sin ninguna advertencia, se lee como secuencia.
Verificado
Especificación de Reactive Streams. Y el propio mapa lo hace bien un centímetro más arriba: la imagen “Flujo de datos asíncronos”, en ese mismo nodo, dibuja tres líneas separadas con una sola señal terminal cada una. El mapa se contradice a sí mismo; hazle caso a esa.

Quédate con la regla, no con el dibujo. Cero o más onNext, y después una sola señal terminal. En cuanto llega onError o onComplete, la conversación se acabó.

Nivel A · Rama 4 · Alternative Implementations

A3 “Reactive socket.io” no se llama así

A3

Un nombre que te lleva a otro proyecto

Cuesta tiempo

Recorte del mapa · rama 4. Api → Alternative Implementations

Dice
Reactive socket.io
Debe decir
RSocket
Por qué importa
Socket.IO (con punto, y muy conocido) es una librería de JavaScript para Node.js que no tiene absolutamente nada que ver: ni es reactiva, ni tiene backpressure, ni es de Java. Si buscas “reactive socket.io” aterrizas ahí y te pasas media hora entendiendo por qué nada encaja. El proyecto que el mapa quiere nombrar se llama RSocket, sin “reactive” delante y sin “.io” dentro.
Curiosidad
El enlace que el propio mapa pone al lado — https://rsocket.io/ — sí es el correcto. El fallo está solo en la etiqueta.
Verificado
rsocket.io (respondiendo 200 en agosto de 2026).

Nivel B · Rama 4 · Alternative Implementations

B1 RSocket no es “un protocolo WebSocket”

B1

Confunde el protocolo con uno de sus transportes

Impreciso
Dice
Web socket protocol with back pressure
Debe decir
Protocolo de aplicación con semántica de Reactive Streams
Por qué importa
RSocket puede viajar sobre WebSocket, pero también sobre TCP y Aeron. Llamarlo “protocolo WebSocket” es como llamar a HTTP “un protocolo TCP”: confunde la capa de aplicación con el transporte de debajo, y te hace pensar que necesitas un navegador para usarlo.
Verificado
Descripción oficial en rsocket.io: “application protocol providing Reactive Streams semantics”, sobre “byte stream transports such as TCP, WebSockets, and Aeron”.

Nivel B · Rama 3 · Features → Otros

B2 “Less latency” promete de más

B2

La métrica que mejora no es esa

Impreciso

Recorte del mapa · rama 3. Features → Otros

Dice
Less latency
Debe decir
Mejor throughput; y mejor latencia de cola, solo bajo saturación
Por qué importa
Tal como está, invita a migrar a WebFlux “para que la API responda más rápido”, y eso no va a pasar. Una petición aislada, con el servidor tranquilo, no se acelera — suele tardar un poco más, por el trabajo extra de coordinación entre operadores y hilos.
Cuándo sí es cierto
Con el servidor saturado. Ahí el modelo bloqueante encola peticiones esperando un hilo libre, y esa cola es latencia pura; el modelo reactivo no la tiene. Así que la latencia de cola (p95, p99) sí mejora — pero por no desperdiciar hilos, que es el beneficio real: throughput.
En una frase
Reactivo no hace que una petición sea más rápida. Hace que quepan más peticiones a la vez. Si mides la latencia de una sola llamada, vas a concluir que no sirve para nada.

Nivel B · Rama 2 · Java Streams vs Reactive Streams

B3 El patrón se llama circuit breaker

B3

Un nombre de patrón mal escrito

Impreciso

Recorte del mapa · rama 2. — en la misma imagen se ve también la errata C2

Dice
Exceptions vs Circuit breaks
Debe decir
Exceptions vs Circuit breakers
Por qué importa
El patrón —el “fusible” que corta las llamadas a un servicio que está fallando para no arrastrarte con él— se llama circuit breaker en toda la literatura y en todas las librerías (Resilience4j, el antiguo Hystrix). “Circuit break” no es un término: si lo buscas así, no encuentras la documentación.
Verificado
Nomenclatura estándar del patrón (Fowler; Resilience4j).

Nivel B · Rama 3 · Reactive Manifesto → Message-Driven

B4 El manifiesto habla de sistemas, no de aplicaciones

B4

Una palabra cambiada que borra la distinción

Impreciso

Recorte del mapa · rama 3. Features → Reactive Manifesto → Message-Driven

Dice
Reactive applications rely on asynchronous message-passing…
Debe decir
Reactive Systems rely on asynchronous message-passing…
Por qué importa
Parece intercambiable y no lo es. El manifiesto habla deliberadamente de sistemas —varios servicios, varias máquinas— porque describe una arquitectura, no una técnica de programación. Cambiar la palabra por “aplicaciones” alimenta justo la confusión más común del tema: creer que por usar Flux ya tienes un sistema reactivo. No: puedes llenar el código de Flux y tener un sistema frágil, y puedes tener un sistema reactivo ejemplar sin una línea de Reactor.
Verificado
reactivemanifesto.org, texto literal. Los otros tres sub-nodos de esa rama sí reproducen el manifiesto con fidelidad.

Para no dejarte una impresión falsa

Lo que sí está bien

Una fe de erratas solo enseña los defectos, y eso deforma. Esto es lo que contrasté contra la fuente y resultó correcto — que es la mayor parte del mapa:

  • ✓Las cinco reglas de Reactive Streams que cita están textuales: son las reglas 4, 5 y 10 del Publisher, la 1 del Subscriber y la 8 de la Subscription.
  • ✓Las cuatro interfaces de java.util.concurrent.Flow y sus descripciones son exactas, y sí llegaron en Java 9.
  • ✓Los tres operadores de backpressure — onBackpressureDrop(), onBackpressureLatest(), onBackpressureBuffer() — existen con esos nombres en Reactor.
  • ✓La escalera de versiones de Java (1 Threads → 5 Executor → 7 Fork/Join → 8 CompletableFuture → 9 Reactive Streams) es correcta en las cinco.
  • ✓Concurrencia vs paralelismo reproduce fielmente la formulación de Rob Pike, y en el sentido correcto.
  • ✓Los diagramas de Cold y Hot Publisher están bien construidos: el frío da secuencias independientes por suscriptor, el caliente una compartida.
  • ✓Las cuatro propiedades del manifiesto son fieles al original (salvo la palabra de B4).
  • ✓La definición de programación reactiva citada de Wikipedia es exacta.
  • ✓Los cinco enlaces del mapa responden 200 a día de hoy.

Y una cosa que no es una errata, sino una fecha. El mapa se dibujó antes de Java 21, así que no menciona los virtual threads — y esos cambiaron parte de su argumento de fondo (“los hilos son caros, por eso reactivo”). Eso no se arregla con una corrección: se explica. Está en la §10 de la guía.

Trazabilidad

Cómo lo verifiqué

Para que puedas repetirlo o desmentirme:

  1. Lectura completa a resolución nativa. El PDF se rasterizó a 4179×5566 px y se recorrió en 19 fragmentos sin reducir, para que ninguna errata de una sola letra se perdiera en el reescalado. Así salieron ExecuterService y lower lever, que a tamaño de pantalla son invisibles.
  2. Clasificación por capas, no por lectura corrida: nombres de clase (¿compila?), nombres de producto (¿existe con ese nombre?), afirmaciones técnicas (¿qué dice la fuente?), enlaces (¿responden?) y ortografía inglesa.
  3. Contraste contra fuentes primarias, no contra tutoriales: la especificación de Reactive Streams, el Javadoc del JDK, el índice de operadores de Reactor, reactivemanifesto.org y rsocket.io.
  4. Segunda pasada adversarial. Cada hallazgo se intentó tumbar antes de darlo por bueno, para no “corregir” lo que ya era correcto. Ahí se cayeron dos falsos positivos míos: un texto que parecía salirse de su recuadro y no se salía, y una regla que creí incompleta y estaba bien.

Qué no cubre esto. Revisé el texto de los nodos y las afirmaciones verificables. Las imágenes incrustadas se revisaron una por una en busca de contradicciones con el contrato — así salió A2 — pero son capturas de terceros y no se auditó su procedencia. Si encuentras una errata número once, es un hallazgo legítimo: este documento no es infalible, solo es sistemático.
