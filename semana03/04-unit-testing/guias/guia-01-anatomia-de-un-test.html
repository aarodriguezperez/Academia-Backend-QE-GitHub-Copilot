El andamiaje

01 El pom.xml, línea a línea

Todo el JUnit que necesitas cabe en una dependencia y un plugin. Merece la pena entender los cuatro bloques, porque es el mismo pom de los otros dos proyectos.

pom.xml — lo que importa 
<!-- 1. El BOM fija la version de TODOS los artefactos de JUnit a la vez -->
<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>org.junit</groupId>
      <artifactId>junit-bom</artifactId>
      <version>6.1.3</version>
      <type>pom</type>  <scope>import</scope>
    </dependency>
  </dependencies>
</dependencyManagement>

<!-- 2. Un solo artefacto agregador. Trae tres cosas dentro:      -->
<!--    junit-jupiter-api    -> lo que ESCRIBES (@Test, Assertions) -->
<!--    junit-jupiter-params -> @ParameterizedTest (guia 03)        -->
<!--    junit-jupiter-engine -> lo que EJECUTA tus tests            -->
<dependency>
  <groupId>org.junit.jupiter</groupId>
  <artifactId>junit-jupiter</artifactId>
  <scope>test</scope>      <!-- 3. no viaja al jar de produccion -->
</dependency>

<!-- 4. Surefire 3.x: quien corre los tests en `mvn test` -->
<plugin>
  <artifactId>maven-surefire-plugin</artifactId>
  <version>3.5.6</version>
</plugin>
ojo Surefire 2.x no valeLas versiones 2.x hablaban directamente con JUnit 4 y no saben pedirle tests a la JUnit Platform. El síntoma es desconcertante: mvn test termina en BUILD SUCCESS con Tests run: 0. No falla — no encuentra nada. Si algún día tu suite “pasa” sospechosamente rápido, mira la versión de Surefire antes que nada.

Sin <version> en la dependencia. No es un olvido: la hereda del BOM. Así, el día que subas a 6.2 cambias un número en un sitio y todos los artefactos de JUnit suben coordinados. Mezclar una api 6.1 con un engine 6.0 es una fuente clásica de errores raros en tiempo de ejecución.

¿Por qué dice 6.1.3 si el tutorial que estás leyendo se llama “JUnit 5”? Porque JUnit 5 dejó de ser la versión actual. Los paquetes siguen siendo org.junit.jupiter.api y las anotaciones son las mismas — no hay nada que reaprender. La historia completa, con la tabla de equivalencias, está en el anexo.

El dominio

02 El código bajo prueba

Dos clases. Una tiene comportamiento y se prueba entera; la otra no tiene ninguno y no se prueba nunca. Esa asimetría ya es una lección.

Alumno.java — el que NO se prueba 
public record Alumno(String matricula, String nombre) {

    public Alumno {
        if (matricula == null || matricula.isBlank()) {
            throw new IllegalArgumentException("La matricula no puede venir vacia");
        }
    }
}

Un record no necesita tests propios. No decide nada: guarda dos cadenas y le pide a Java el equals(), el hashCode() y el toString(). Probar eso es probar el compilador. Lo único con criterio propio es la validación del constructor compacto — y esa la cubre BoletaTest de paso. Se prueba el código que decide.

Boleta.java — las tres reglas 
public static final double MINIMA_APROBATORIA = 70.0;

// Regla 1: una calificacion valida va de 0 a 100
public void registrar(String materia, int calificacion) {
    if (calificacion < 0 || calificacion > 100) {
        throw new IllegalArgumentException("Calificacion fuera de rango: " + calificacion);
    }
    calificaciones.put(materia, calificacion);
}

// Regla 2: el promedio es la media. Una boleta vacia promedia 0.
public double promedio() {
    if (calificaciones.isEmpty()) return 0.0;
    double suma = 0;
    for (int c : calificaciones.values()) suma += c;
    return suma / calificaciones.size();
}

// Regla 3: se aprueba con 70 O MAS. Borrar el '=' de ese >=
// es UN SOLO caracter, y es todo el tema de la seccion 07.
public boolean aprobado() {
    return promedio() >= MINIMA_APROBATORIA;
}

Guarda esa tercera regla. «Se aprueba con 70 o más» sale del reglamento de la academia, no del código. Un test que se escribe desde el reglamento comprueba el 70. Un test que se escribe mirando el código ya escrito comprueba lo que el código haga — y si el código dice >, el test lo bendice.

El código

03 Tu primer test

Un test es un método de Java con tres características y ni una más: lleva @Test encima, no devuelve nada, y termina en una aserción.

PrimerTest.java 
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.assertEquals;

class PrimerTest {                          // ni public, ni "extends" nada

    @Test
    void unaBoletaRecienCreadaPromediaCero() {

        // 1. PREPARAR: monta el escenario
        Alumno ana = new Alumno("A01", "Ana Torres");
        Boleta boleta = new Boleta(ana);

        // 2. ACTUAR: ejecuta lo que quieres probar
        double promedio = boleta.promedio();

        // 3. COMPROBAR: una sola pregunta, con respuesta si o no
        assertEquals(0.0, promedio);
    }
}

Ese comentario en tres pasos —preparar, actuar, comprobar— no es decoración. Es la estructura de prácticamente todo test que vas a escribir en tu vida, y cuando un test no cabe en esos tres bloques suele ser señal de que está probando dos cosas a la vez.

Tres detalles que sorprenden

01 Ni la clase ni el método son publicJUnit 4 lo exigía. Jupiter no: le basta con acceso de paquete, y es lo idiomático. Si vienes de tutoriales viejos, verás public por todas partes — no está mal, sobra.
02 El nombre del método es documentaciónCuando el test falle, lo primero que verás en la consola es ese nombre. unaBoletaRecienCreadaPromediaCero se lee como una frase; test1 no dice nada a las once de la noche.
03 El esperado va PRIMEROassertEquals(esperado, real). Al revés compila igual y el test pasa igual — solo se nota el día que falla, y entonces el mensaje te miente al derecho: dirá expected: <90> cuando 90 era el resultado. Error caro y silencioso.

@DisplayName y el tercer parámetro

@Test
@DisplayName("Con 90 de promedio, el alumno aprueba")
void aprobarConNoventa() {
    Boleta boleta = new Boleta(new Alumno("A01", "Ana Torres"));
    boleta.registrar("Java", 90);

    assertTrue(boleta.aprobado(), "Con 90 de promedio deberia aprobar");
    //                              ^ esto NO se lee cuando el test pasa.
    //                                Se lee el dia que se pone en rojo.
}

@DisplayName sirve para lo que el nombre del método no puede: espacios, acentos, dos puntos. Regla práctica: el nombre del método para quien lee el código, el @DisplayName para quien lee el reporte.

Y el tercer parámetro de la aserción es el mensaje de fallo. Compara lo que vería alguien depurando de madrugada:

Sin mensajeexpected: <true> but was: <false> — cierto, e inútil. ¿Qué regla se rompió?
Con mensajeCon 90 de promedio deberia aprobar — ahí está la regla del negocio, en el reporte.

04 El ciclo de vida

Cuatro anotaciones controlan qué corre antes y después de cada test. Corre CicloDeVidaTest y mira el orden en la consola:

$ ./mvnw test -Dtest=CicloDeVidaTest

== @BeforeAll  -- una sola vez, antes de todo
   -> @BeforeEach -- boleta nueva y limpia
   <- @AfterEach  -- llevamos 1 test(s)
   -> @BeforeEach -- boleta nueva y limpia
   <- @AfterEach  -- llevamos 2 test(s)
   -> @BeforeEach -- boleta nueva y limpia
   <- @AfterEach  -- llevamos 3 test(s)
== @AfterAll   -- una sola vez, al final. Corrieron 3 tests
AnotaciónCuándo correPara qué
@BeforeAllUna vez, antes del primer test. Debe ser static.Montaje caro y compartido: abrir una conexión, levantar un contenedor.
@BeforeEachAntes de cada test.El escenario limpio. Es la que vas a usar el 90 % de las veces.
@AfterEachDespués de cada test, aunque falle.Limpiar lo que el test ensució.
@AfterAllUna vez, al final. static.Cerrar lo que abrió @BeforeAll.

Por qué @BeforeAll tiene que ser static

No es un capricho de la API. Es la consecuencia de una decisión de diseño que conviene entender bien, porque explica media docena de comportamientos:

JUnit crea una instancia nueva de tu clase de test por cada @Test. No una por clase: una por método. Si @BeforeAll no fuera static, no habría ninguna instancia a la que pertenecer cuando corre — todavía no existe ninguna.

Y esa misma decisión es la que impide que te pases datos entre tests por un campo. El proyecto lo demuestra con un test que se comprueba a sí mismo:

CicloDeVidaTest.java — la demostración 
private int contadorDeInstancia = 0;      // NO es static

@Test
@DisplayName("Cada test corre sobre una INSTANCIA NUEVA de la clase")
void cadaTestEsUnaInstanciaNueva() {
    contadorDeInstancia++;
    assertEquals(1, contadorDeInstancia,
            "Si esto fuera 2, JUnit habria reutilizado la instancia");
}

Por muchas veces que corras la clase, el contador vale 1. De ahí sale la regla práctica más importante de esta sección: no uses campos de instancia para pasar datos entre tests. No funciona — y el día que parezca funcionar, será porque el orden de ejecución te dio la razón por accidente.

Esa decisión se puede desactivar con @TestInstance(PER_CLASS), y hay un caso en que vale la pena. Está en la guía 02, con el aviso correspondiente.

El catálogo

05 Las aserciones

Todas viven en la misma clase — org.junit.jupiter.api.Assertions — y todas son static. De ahí el import static.

AserciónCompruebaNota
assertEqualsIgualdad con equals()Para double lleva un tercer parámetro: la tolerancia. Ver §06.
assertTrue / assertFalseUn booleanoSin mensaje, su fallo es el menos informativo de todos. Ponlo siempre.
assertNull / assertNotNullReferencias nulas
assertSame / assertNotSameIdentidad con ==Distinto de assertEquals: dos record con los mismos datos son equals pero no same.
assertArrayEqualsArreglos, posición a posiciónassertEquals sobre arreglos compara referencias y siempre fallaría.
assertIterableEqualsColecciones: mismos elementos, mismo ordenEl tipo de colección no importa.
assertLinesMatchTexto línea a línea, admitiendo expresiones regularesPara salidas donde una parte es variable.
assertThrowsQue algo lance una excepciónTema completo en la guía 02.
assertAllVarias aserciones de golpeLa más importante de la lista. Sigue leyendo.

assertAll: no enterarse de un fallo a la vez

Cuatro aserciones seguidas se comportan como un cortocircuito: en cuanto la primera falla, las demás ni se ejecutan. Arreglas esa, corres otra vez, y descubres que la segunda también fallaba. Tres iteraciones después sigues ahí.

@Test
void todasLasAsercionesDeUnGolpe() {
    assertAll("estado completo de la boleta",
            () -> assertEquals("A01", boleta.alumno().matricula()),
            () -> assertEquals("Ana Torres", boleta.alumno().nombre()),
            () -> assertEquals(2, boleta.totalMaterias()),
            () -> assertEquals(80.0, boleta.promedio()),
            () -> assertTrue(boleta.aprobado()));
}

Las ejecuta todas y reporta juntas las que fallaron. Una sola corrida, la foto completa del daño. Regla: si las aserciones describen el mismo objeto desde varios ángulos, van dentro de un assertAll.

El mensaje perezoso

// El String se construye SIEMPRE, aunque el test pase:
assertTrue(boleta.aprobado(), "Fallo con promedio " + boleta.promedio());

// El Supplier solo se construye si el test FALLA:
assertTrue(boleta.aprobado(), () -> "Fallo con promedio " + boleta.promedio());

En un test suelto da igual. En una suite de cuatro mil tests que concatenan cadenas en cada aserción, deja de dar igual.

La primera sorpresa

06 La trampa de los decimales

El promedio de 70, 80 y 85 es 235 entre 3. Abre DecimalesTest y descomenta la línea marcada:

// assertEquals(78.33, promedio);   // <-- DESCOMENTA ESTO
$ ./mvnw test -Dtest=DecimalesTest

[ERROR] DecimalesTest.laTrampa:64 expected: <78.33> but was: <78.33333333333333>

El test no está mal escrito y el código no está roto. Pediste una igualdad exacta sobre un número que no es exacto. Un double no puede guardar 78.3333…: guarda el más cercano que sabe representar. No es un fallo de Java ni de JUnit — es el punto flotante (IEEE 754) funcionando como funciona en todos los lenguajes. Por eso 0.1 + 0.2 tampoco da 0.3.

La solución es el tercer parámetro de assertEquals para double: la tolerancia.

assertEquals(78.33, boleta.promedio(), 0.01);
//                                    ^ "acepto cualquier valor que no
//                                       se aleje mas de una centesima"

No es hacer trampa: es declarar con cuánta precisión te importa el resultado, que es una decisión de negocio, no de programación. Para calificaciones, dos decimales sobran.

Si el valor es…Usa
int, long, String, boolean, enum, recordassertEquals sin tolerancia
double, floatassertEquals con tolerancia
dineroNi double ni float: BigDecimal

Esa última fila no es un detalle de tests. Es la razón por la que ningún sistema bancario guarda pesos en un double.

07 El test que atrapa el bug

Aquí es donde toda la guía cobra sentido. Vamos a meter un bug de un solo carácter en Boleta.aprobado() y a ver qué hace la suite.

$ ./scripts/ver-fallar.sh

El script hace cuatro cosas: corre la suite tal cual, cambia el >= por >, vuelve a correrla, y deja el código como estaba. Esto es lo que sale:

salida real de ver-fallar.sh

   BUILD SUCCESS -- los 22 tests en verde.

== 2. Metemos el bug: 'promedio() >= 70' pasa a 'promedio() > 70' ==
   74:        return promedio() > MINIMA_APROBATORIA;   // BUG INYECTADO
   Un caracter. El alumno que saca exactamente 70 ahora reprueba.

Veinte de veintidós tests siguieron en verde con el bug dentro. Los que probaban «90 aprueba» y «50 reprueba» no se enteraron de nada: estaban lejos de la frontera, y el bug solo vive en la frontera. De los veintidós tests que escribiste, dos hicieron todo el trabajo.

Y estos son los dos:

BoletaTest.java — el test que importa 
@Test
@DisplayName("EL LIMITE: con exactamente 70 se aprueba, con 69 no")
void elLimiteExacto() {
    Boleta justo = new Boleta(new Alumno("A02", "Beto Ruiz"));
    justo.registrar("Java", 70);
    assertTrue(justo.aprobado(),
            "70 es aprobatorio: el reglamento dice '70 o mas'");

    // el limite menos uno
    Boleta porDebajo = new Boleta(new Alumno("A03", "Carla Diaz"));
    porDebajo.registrar("Java", 69);
    assertFalse(porDebajo.aprobado(), "69 no alcanza");

    // el limite mas uno
    Boleta porEncima = new Boleta(new Alumno("A04", "Dario Luna"));
    porEncima.registrar("Java", 71);
    assertTrue(porEncima.aprobado(), "71 aprueba de sobra");
}

El segundo es más sutil: dos materias que promedian 70 sin que ninguna valga 70. Si alguien «arregla» el bug comparando calificaciones sueltas en lugar del promedio, ese lo caza.

Lo que acabas de comprobar

No todos los tests valen lo mismo. La cobertura de aprobado() era del 100 % antes y después de meter el bug — y aun así el bug pasó por delante de veinte tests sin que ninguno se moviera. Cobertura alta no es lo mismo que estar protegido.

La receta, entonces. Para cada regla que tenga una frontera, escribe tres casos: el límite, el límite menos uno y el límite más uno. Y añade siempre el vacío y el nulo. Cinco casos por regla, y habrás cubierto donde vive prácticamente todo bug real.

Referencia

08 Trampas y ejercicios

Lo que te vas a encontrar

01 Tests run: 0 y BUILD SUCCESSNo falló: no encontró nada. Causas: Surefire 2.x, la clase no termina en Test, o el archivo está en src/main/java en vez de src/test/java.
02 @BeforeAll no compilaFalta el static. El mensaje de JUnit lo dice, pero se lee tarde porque llega en ejecución, no al compilar.
03 expected: <78.33> but was: <78.33333333333333>Falta la tolerancia en un assertEquals sobre double. Sección 06.
04 El segundo test ve datos del primeroEstás usando un campo de instancia como si sobreviviera, o un static que sí sobrevive. Monta el escenario en @BeforeEach.
05 expected y actual parecen invertidosLo están: assertEquals(esperado, real), en ese orden.
06 El test pasa pero no comprueba nada¿Hay alguna aserción? Un método con @Test y sin assert siempre pasa, y cuenta en el reporte como un test más.

Ejercicios

  • 1Predice antes de correr Antes de ejecutar ver-fallar.sh, escribe en un papel cuáles de los 22 tests crees que van a fallar. Después córrelo. ¿Cuadró?
  • 2Otro bug de un carácter Cambia en registrar() el > 100 por >= 100. ¿Qué test lo caza? Si ninguno, escríbelo — y fíjate en qué valor tuviste que elegir.
  • 3El límite que falta promedio() devuelve 0 para una boleta vacía. ¿Es correcto que una boleta sin materias «promedie cero» y por tanto repruebe? Escribe el test que documente la decisión que tomes, con su mensaje explicando por qué.
  • 4Rompe un test a propósito Cambia un assertEquals(80.0, …) por assertEquals(81.0, …) y lee el fallo entero. Identifica las tres partes de la sección 05 de la guía 00.
  • 5Convierte a assertAll En BoletaTest.extremosDelRango hay dos aserciones sueltas. Rompe las dos a la vez y observa que solo te enteras de una. Ahora envuélvelas en assertAll y repite.
  • 6El test que no debería existir Escribe un test para Alumno.nombre(). Míralo. ¿Qué te protege exactamente? Ese es el tipo de test que infla el número del reporte y no protege nada.

Si trabajas en Windows. Usa mvnw.cmd test en lugar de ./mvnw test. El script ver-fallar.sh necesita Git Bash o WSL; en PowerShell no corre.
