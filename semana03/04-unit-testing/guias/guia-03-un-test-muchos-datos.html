El código bajo prueba es un validador de CURP. Está elegido por un motivo muy concreto: tiene decenas de casos que probar y todos se prueban igual, cambiando solo el dato.

El problema

01 El problema, y @ValueSource

Así se prueban cuatro CURP válidas con lo que sabes hasta ahora:

@Test void valida1() { assertTrue(ValidadorCurp.esValida("RUGM800101HNLZRK09")); }
@Test void valida2() { assertTrue(ValidadorCurp.esValida("TOLA010615MNLRPNA5")); }
@Test void valida3() { assertTrue(ValidadorCurp.esValida("MAAJ990228HDFRRS08")); }
@Test void valida4() { assertTrue(ValidadorCurp.esValida("XEXX010101HNEXXXA4")); }

Cuatro métodos idénticos salvo por una cadena. Y con dos consecuencias malas: añadir el quinto caso cuesta copiar y pegar — así que nadie lo hace — y si cambia la regla hay que tocar cuatro sitios.

ValueSourceTest.java — lo mismo, en un método 
@ParameterizedTest(name = "[{index}] {0} es una CURP con estructura valida")
@ValueSource(strings = {
        "RUGM800101HNLZRK09",     // 1980-01-01, hombre, Nuevo Leon
        "TOLA010615MNLRPNA5",     // 2001-06-15, mujer, Nuevo Leon
        "MAAJ990228HDFRRS08",     // 1999-02-28, hombre, CDMX
        "XEXX010101HNEXXXA4"      // la CURP generica de extranjero
})
void curpsValidas(String curp) {
    assertTrue(ValidadorCurp.esValida(curp), "Deberia ser valida: " + curp);
}

Sigue siendo cuatro tests. En el reporte aparecen como cuatro entradas independientes: si el tercero falla, los otros tres siguen en verde y sabes exactamente cuál cayó. No es «un test con cuatro datos» — es un método que produce cuatro tests.

Dos cambios respecto a un @Test, y los dos se olvidan

  • 1@ParameterizedTest en lugar de @Test No además. Si dejas los dos, JUnit ejecuta el método dos veces de dos maneras distintas y falla de forma confusa.
  • 2Ahora el método sí recibe parámetros Uno por columna, en orden.

El atributo name vale los diez segundos que cuesta

Sin name[1], [2], [3]. Cuando el 7 falla, no sabes qué dato era.
Con name[3] MAAJ990228HDFRRS08 es una CURP…. El dato que falló, en el reporte.

Marcadores disponibles: {index}, {0} {1}… por posición, y {argumentsWithNames}.

Los casos que no pasan, y una regla al escribirlos

@ParameterizedTest(name = "[{index}] {0} NO es valida")
@ValueSource(strings = {
        "RUGM800101HNLZRK0",      // 17 caracteres: falta el verificador
        "RUGM800101HNLZRK099",    // 19: sobra uno
        "RBGM800101HNLZRK09",     // la 2a posicion debe ser vocal (o X); B no
        "RUGM801301HNLZRK09",     // mes 13
        "RUGM800132HNLZRK09",     // dia 32
        "RUGM800101XNLZRK09",     // sexo X: solo H o M
        "RUGM800101HXXZRK09",     // XX no es una entidad federativa
        "RUGM800101HNLAEK09",     // A y E son vocales donde van consonantes
        "rugm800101hnlzrk09"      // minusculas
})
void curpsInvalidas(String curp) {
    assertFalse(ValidadorCurp.esValida(curp), "No deberia ser valida: " + curp);
}

Cada dato rompe UNA sola regla. Si uno rompiera dos, el test seguiría en verde aunque el validador solo detectara una — y no te enterarías. Un caso inválido por cada motivo, nunca uno que los junte todos.

El null y el vacío tienen su propia fuente

@ParameterizedTest
@NullAndEmptySource                          // = @NullSource + @EmptySource
@ValueSource(strings = { " ", "   ", "\t" })  // y de paso, solo espacios
void nadaEsValido(String curp) {
    assertFalse(ValidadorCurp.esValida(curp));
}

@ValueSource no puede producir null: las anotaciones de Java no admiten null en sus arreglos. Por eso existen aparte. Y merecen su propio test siempre — el null y el vacío son, por mucho, los dos valores que más veces tumban código en producción.

Las fuentes se apilan y los datos se suman. Ese método corre 1 (null) + 1 (vacío) + 3 (@ValueSource) = 5 veces.

El código

02 Varias columnas: @CsvSource

@ValueSource solo da un valor por corrida. En cuanto necesitas «esta entrada produce este resultado» hacen falta al menos dos columnas.

CsvSourceTest.java — la tabla de límites 
@ParameterizedTest(name = "{0} -> {1}")
@CsvSource({
        "100, EXCELENTE",
        " 90, EXCELENTE",     // limite exacto
        " 89, BUENO",         // uno menos
        " 80, BUENO",         // limite exacto
        " 79, SUFICIENTE",    // uno menos
        " 70, SUFICIENTE",    // limite exacto
        " 69, INSUFICIENTE",  // uno menos
        "  1, INSUFICIENTE",
        "  0, INSUFICIENTE"
})
void tablaDeNiveles(int calificacion, Nivel esperado) {
    assertEquals(esperado, Calificador.nivelDe(calificacion));
}

Ahí están los tres límites y sus vecinos de abajo. 90/89, 80/79, 70/69. Eso es la receta de la guía 01 — el límite y el límite menos uno — aplicada tres veces, y cuesta seis líneas en vez de seis métodos. Ese es el verdadero cambio: añadir un caso límite deja de dar pereza.

Y fíjate en que la tabla se lee como una especificación. Un analista que no programa puede revisarla y decir «falta el caso del 100».

JUnit convierte los tipos solo

El String "90" llega como int, "EXCELENTE" llega como Nivel.EXCELENTE, "1980-01-01" llega como LocalDate. No hay que parsear nada. Se llama conversión implícita.

delimitador propio y bloque de texto 
@ParameterizedTest(name = "{1}")
@CsvSource(delimiter = '|', textBlock = """
        RUGM800101HNLZRK09 | 1980-01-01 | HOMBRE | NL
        TOLA010615MNLRPNA5 | 2001-06-15 | MUJER  | NL
        MAAJ990228HDFRRS08 | 1999-02-28 | HOMBRE | DF
        """)
void desglosarLaCurp(String curp, LocalDate fecha, Sexo sexo, String entidad) {
    assertAll("todo lo que se puede sacar de " + curp,
            () -> assertTrue(ValidadorCurp.esValida(curp)),
            () -> assertEquals(fecha,   ValidadorCurp.fechaNacimiento(curp)),
            () -> assertEquals(sexo,    ValidadorCurp.sexo(curp)),
            () -> assertEquals(entidad, ValidadorCurp.entidad(curp)));
}

AtributoPara qué
numLinesToSkip = 1Saltarse la cabecera. Si se te olvida, JUnit intenta convertir la palabra curp en… una CURP, y el fallo no dirá «te faltó la cabecera»: hablará de una conversión imposible. Vale la pena reconocerlo a la primera.
nullValues = ""Las celdas vacías llegan como null. Sin esto llegan como cadena vacía y la conversión a enum truena.

Cuándo un archivo en vez de la anotación: cuando hay muchas filas (a partir de diez o quince, la anotación estorba), cuando el archivo lo mantiene alguien que no toca el código, o cuando los datos salen de una exportación de la base de datos.

El caso estrella

03 El 29 de febrero

Estas dos CURP dicen «29 de febrero». Se diferencian en un carácter, el número 17 — la homoclave — y eso decide el siglo:

RUGM990229HNLZRK09    homoclave DIGITO -> 1999 -> no fue bisiesto  INVALIDA
RUGM000229HNLZRKA9    homoclave LETRA  -> 2000 -> SI fue bisiesto  valida

(2000 es bisiesto porque es divisible entre 400. 1900 no lo fue.)

Ninguna expresión regular puede distinguirlas. Para el patrón las dos son «día 29 del mes 02», y las dos encajan. Hace falta un calendario de verdad.

ValidadorCurp.java — las dos capas 
public static boolean esValida(String curp) {
    if (curp == null || !PATRON.matcher(curp).matches()) {
        return false;                // capa 1: el FORMATO
    }
    return fechaReal(curp) != null;    // capa 2: el SIGNIFICADO
}

// La regla del siglo: homoclave numerica -> 1900s, alfabetica -> 2000s
private static LocalDate fechaReal(String curp) {
    int siglo = Character.isDigit(curp.charAt(16)) ? 1900 : 2000;
    try {
        return LocalDate.of(siglo + anio, mes, dia);
    } catch (DateTimeException e) {
        return null;                  // 29-feb de un anio no bisiesto
    }
}

Y el test que protege la segunda capa — la única que ninguna otra cosa protege:

@ParameterizedTest(name = "{0} -> valida={1} ({2})")
@CsvSource({
        "RUGM990229HNLZRK09, false, 1999 no fue bisiesto",
        "RUGM000229HNLZRKA9, true,  2000 si fue bisiesto",
        "RUGM040229HNLZRKA9, true,  2004 bisiesto normal",
        "RUGM010229HNLZRKA9, false, 2001 no fue bisiesto"
})
void elVeintinueveDeFebrero(String curp, boolean esperada, String porque) {
    assertEquals(esperada, ValidadorCurp.esValida(curp), porque);
}

La tercera columna no se afirma. No aparece en ninguna aserción: solo entra en el nombre de la corrida. Y ahí convierte el reporte en documentación legible — RUGM990229HNLZRK09 -> valida=false (1999 no fue bisiesto). Es un truco barato y muy rentable.

La lección general, más allá de la CURP

El formato y el significado son dos validaciones distintas, y confundirlas deja pasar datos imposibles. Un correo con arroba puede no existir; un código postal con cinco dígitos puede no corresponder a ningún lugar; una fecha con día 31 puede caer en un mes de 30. Si tu validación es solo un regex, ya sabes qué te falta probar.

04 Cuando no cabe en una anotación

@ValueSource y @CsvSource solo aceptan constantes: cadenas, números, clases. Es una limitación de Java, no de JUnit — una anotación no puede contener un objeto construido en tiempo de ejecución.

@ParameterizedTest(name = "{0} -> {1}, {2}, {3}")
@MethodSource("curpsConSuContenido")
void desglosarConObjetosReales(String curp, LocalDate fecha, Sexo sexo, String entidad) {
    assertEquals(fecha, ValidadorCurp.fechaNacimiento(curp));
    // …
}

static Stream<Arguments> curpsConSuContenido() {
    return Stream.of(
            Arguments.of("RUGM800101HNLZRK09", LocalDate.of(1980, 1, 1),  Sexo.HOMBRE, "NL"),
            Arguments.of("TOLA010615MNLRPNA5", LocalDate.of(2001, 6, 15), Sexo.MUJER,  "NL"),
            Arguments.of("RUGM000229HNLZRKA9", LocalDate.of(2000, 2, 29), Sexo.HOMBRE, "NL"));
}

La ventaja sobre @CsvSource: los valores son objetos de verdad, construidos en Java, con el compilador vigilando. Si te equivocas de tipo, no compila. En un CSV te enterarías en ejecución.

Reglas del método proveedor
staticSalvo con @TestInstance(PER_CLASS), que viste en la guía 02.
Sin parámetros
DevuelveStream, Collection, Iterator o un arreglo.
Un parámetroStream<String>, IntStream…
Varios parámetrosStream<Arguments>

Lo que ninguna anotación puede hacer: datos calculados

@ParameterizedTest(name = "entidad {0}")
@MethodSource("todasLasEntidades")
void cualquierEntidadValidaSeAcepta(String entidad) {
    String curp = "RUGM800101H" + entidad + "ZRK09";
    assertTrue(ValidadorCurp.esValida(curp));
}

static Stream<String> todasLasEntidades() {
    return ValidadorCurp.entidadesValidas().stream().sorted();
}

Ventaja real, no teórica: el día que se añada una entidad federativa, el test la cubre solo. Un @ValueSource con las 33 escritas a mano habría que actualizarlo — y nadie se acuerda.

Lo mismo con bucles: IntStream.rangeClosed(1, 12) genera los doce meses en una línea. A mano serían doce métodos o un @ValueSource que nadie querría revisar.

Un proveedor en otra clase

@MethodSource("com.academymty.academia.CatalogoDeCurps#lasValidas")
//             ruta completa de la clase          ^ y # antes del metodo

Así se comparte un catálogo de datos entre varias clases de test sin duplicarlo. Es lo que se hace en proyectos grandes: una clase DatosDePrueba con los casos canónicos. CatalogoDeCurps no tiene ni un @Test — y Surefire no la ejecuta porque su nombre no termina en Test.

05 La fuente que se actualiza sola

@EnumSource tiene una propiedad que ninguna otra fuente tiene, y es la razón de usarla siempre que haya un enum de por medio:

El día que alguien añada una constante al enum, este test la prueba sin que nadie lo toque. Con un @ValueSource escribirías los cuatro niveles a mano, llegaría un quinto, y el test seguiría en verde sin haberlo probado nunca. Ese es el fallo silencioso más común al probar enum.

@ParameterizedTest(name = "{0}")
@EnumSource                                // sin atributos: TODAS las constantes.
void todoNivelSabeSiEsAprobatorio(Nivel nivel) {   // JUnit deduce el enum de la firma

    // La regla, expresada de forma que aguante niveles nuevos:
    assertEquals(nivel != Nivel.INSUFICIENTE, nivel.esAprobatorio());
}
FormaQué selecciona
@EnumSourceTodas las constantes del tipo del parámetro.
@EnumSource(names = {"EXCELENTE", "BUENO"})Solo esas.
@EnumSource(mode = EXCLUDE, names = "INSUFICIENTE")Todas menos esa.
@EnumSource(mode = MATCH_ALL, names = ".*E$")Las que casan con la expresión regular.

Prefiere EXCLUDE a listar las incluidas cuando la excepción es corta. «Todas menos X» envejece bien: si mañana se añade un nivel nuevo, entra automáticamente. «Estas tres» no envejece — se queda obsoleto en silencio.

El test de ida y vuelta

@ParameterizedTest
@EnumSource
void idaYVueltaDelSexo(Sexo sexo) {
    assertEquals(sexo, Sexo.desdeLetra(sexo.letra()));
}

Los tests de ida y vuelta son de los más rentables que existen: una sola línea cubre dos métodos y garantiza que no se desincronicen. Y si el enum crece, crecen solos.

El código

06 Repetir, y cuándo no

Empecemos por lo que no es, porque es el mal uso más frecuente:

no @RepeatedTest NO es para tests inestablesSi un test falla una de cada diez veces, repetirlo diez veces no lo arregla: lo esconde mejor. Un test inestable señala un bug real — casi siempre una condición de carrera, o una dependencia del reloj o del orden — y taparlo con repeticiones es cambiar una señal por ruido.

Para lo que sí sirve: código con aleatoriedad dentro, comprobar que una operación es idempotente, o provocar a propósito problemas de concurrencia.

@RepeatedTest(value = 10, name = "CURP al azar {currentRepetition} de {totalRepetitions}")
void cualquierCurpGeneradaEsValida() {
    String curp = curpAlAzar();
    assertTrue(ValidadorCurp.esValida(curp), "Se genero una CURP invalida: " + curp);
}

{currentRepetition} y {totalRepetitions} son marcadores propios de @RepeatedTest. Sin ellos las diez corridas se llaman igual y no sabes cuál cayó.

RepetitionInfo: que cada repetición haga algo distinto

@RepeatedTest(value = 28, name = "dia {currentRepetition} del mes")
void losVeintiochoDias(RepetitionInfo info) {
    int dia = info.getCurrentRepetition();
    String curp = String.format("RUGM8001%02dHNLZRK09", dia);

    assertTrue(ValidadorCurp.esValida(curp), "El dia " + dia + " deberia valer");
}

Se inyecta igual que el TestInfo de la guía 02: lo pides por parámetro y JUnit te lo da.

Y la semilla del Random es fija a propósito. Un test con aleatoriedad sin semilla es un test que no se puede reproducir: falla el martes, lo corres el miércoles y pasa, y te quedas sin saber qué dato lo tumbó. new Random(20260826L) — la misma secuencia siempre.

07 Tests que no existen hasta que corres

Un @Test lo descubre JUnit antes de ejecutar nada, leyendo las anotaciones. Un @ParameterizedTest también: sus datos están en el código o en un archivo del classpath.

Un @TestFactory es distinto: es un método que se ejecuta y devuelve tests. Los casos pueden salir de donde sea — una consulta a la base de datos, una llamada a un API, un archivo que no existía al compilar.

@TestFactory
Stream<DynamicTest> unTestPorFilaDelArchivo() throws IOException {
    return leerCsv("/curps-validas.csv").stream()
            .map(fila -> dynamicTest(
                    "fila: " + fila[0] + " (" + fila[1] + ")",   // nombre: un String normal
                    () -> {                                     // cuerpo: una lambda
                        assertTrue(ValidadorCurp.esValida(fila[0]));
                        // …
                    }));
}

Con @CsvFileSource también se lee un archivo, sí — pero el nombre tiene que estar escrito en la anotación, es decir, decidido al compilar. Aquí el archivo podría elegirse por una variable de entorno, bajarse de un servidor o listarse de un directorio.

La letra pequeña, y es importante

ojo @BeforeEach corre una vez por @TestFactory, NO por cada test dinámicoEs la fuente número uno de sorpresas con esta anotación. Si cada caso necesita su escenario limpio, móntalo dentro de la lambda de cada dynamicTest — no confíes en el @BeforeEach.

El proyecto lo demuestra con un test que se comprueba a sí mismo: elCicloDeVidaNoAplica() devuelve tres tests dinámicos y los tres miran el mismo contador. No sube — se queda clavado.

DynamicContainer: el árbol, pero generado

DynamicContainer.dynamicContainer("entidad " + entidad, Stream.of(
        dynamicTest("la CURP es valida",          () -> …),
        dynamicTest("se lee de vuelta como " + entidad, () -> …)));

Es lo que hacía @Nested con los tests estáticos, pero construido al vuelo.

Regla práctica: si puedes con @ParameterizedTest, usa @ParameterizedTest. @TestFactory es para cuando los casos no se conocen hasta el momento de correr. Es más potente y bastante más fácil de escribir mal.

Escribir el caso 212 no cuesta un método nuevo: cuesta una línea en una tabla. Y ahí está el verdadero cambio — no es que escribas menos código, es que añadir un caso deja de dar pereza. Los casos límite se prueban cuando probarlos es barato.

Referencia

09 Trampas y ejercicios

01 @Test y @ParameterizedTest juntosEs uno en lugar del otro. Con los dos, JUnit ejecuta el método dos veces de dos maneras y el fallo es difícil de leer.
02 ParameterResolutionExceptionEl número o el tipo de los parámetros no cuadra con las columnas de la fuente. Cuenta las comas.
03 Un error de conversión en la primera fila de un CSVFalta numLinesToSkip = 1: está intentando convertir la cabecera en datos.
04 Una celda vacía revienta la conversión a enumFalta nullValues = "". Sin eso, la celda llega como cadena vacía, no como null.
05 @MethodSource no encuentra el proveedor¿Es static? ¿Tiene parámetros (no debe)? ¿El nombre está bien escrito? Si vive en otra clase, la ruta completa y #.
06 Los tests dinámicos comparten estado sin quererEl @BeforeEach corrió una sola vez, no por cada uno. Monta el escenario dentro de cada lambda.
