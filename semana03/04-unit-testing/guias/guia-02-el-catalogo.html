El código

01 Probar que algo truena

Un test normal comprueba que el código hace lo que debe. Este comprueba lo contrario: que se niega a hacer lo que no debe.

assertThrows(CupoLlenoException.class, () -> java101.inscribir("A03"));
//           ^ tipo esperado             ^ lambda: NO se ejecuta hasta
//                                          que assertThrows la llama

La lambda no es adorno, es el mecanismo. Si escribieras assertThrows(CupoLlenoException.class, java101.inscribir("A03")), el método correría antes de entrar en assertThrows y la excepción tumbaría el test. La lambda es código empaquetado, todavía sin ejecutar — por eso funciona.

assertThrows devuelve la excepción

Y eso cambia todo: dejas de comprobar solo el tipo y pasas a comprobar el contenido.

CupoLlenoException ex = assertThrows(CupoLlenoException.class,
        () -> java101.inscribir("A03"));

assertAll("lo que trae la excepcion dentro",
        () -> assertEquals("JAVA-101", ex.claveCurso()),
        () -> assertEquals(2, ex.cupo()),
        () -> assertTrue(ex.getMessage().contains("JAVA-101"),
                "El mensaje deberia nombrar el curso, para el log"));

Esta es la razón por la que el dominio tiene su propia CupoLlenoException con campos dentro, en lugar de lanzar un RuntimeException genérico: los campos se pueden afirmar; el texto del mensaje no debería. Un test que compara mensajes se rompe el día que alguien corrige una tilde, sin que nada esté mal.

La trampa: assertThrows acepta subclases

ojo assertThrows(RuntimeException.class, …) casi siempre pasaAcepta el tipo pedido y todas sus subclases. Un NullPointerException también es RuntimeException — así que ese test daría por bueno precisamente el bug que querías evitar. Habrías escrito un test que aprueba el fallo. Pide siempre el tipo concreto que el contrato promete.

Si lo que quieres probar es la jerarquía, hazlo explícito con assertInstanceOf:

RuntimeException ex = assertThrows(RuntimeException.class, () -> java101.inscribir("A03"));
assertInstanceOf(CupoLlenoException.class, ex,
        "Pediste RuntimeException y te dieron algo mas concreto");

Y el reverso, assertDoesNotThrow, con cuidado. Cualquier test que pase ya demuestra que no hubo excepción — si la hubiera, estaría en rojo. Solo vale la pena cuando lo que quieres documentar es la ausencia del fallo: «el último lugar todavía se puede ocupar, no se cae por uno de más».

El código

02 Probar el tiempo

Curso.actaDeInscripcion() tarda 40 ms por alumno. Es una simulación, pero el problema que representa es real: un reporte que crece con los datos y un día deja de caber en la ventana de respuesta.

Hay dos familias de timeout, y la diferencia entre ellas es la que confunde a todo el mundo.

assertTimeoutassertTimeoutPreemptively
¿Interrumpe?No. Espera a que termine y después compara.Sí. Aborta al cumplirse el plazo.
¿Qué hilo?El del test. Lo normal y lo seguro.Otro hilo.
Si tarda 10 min……el test tarda 10 min y luego se pone en rojo.…el test corta en el plazo que pusiste.
Cuándo usarlaPor defecto.Solo si el riesgo real es que el código se cuelgue para siempre.

La letra pequeña de assertTimeoutPreemptively, la que cuesta una tarde de depuración: ese «otro hilo» significa que todo lo que viva en un ThreadLocal deja de estar ahí. Transacciones de Spring, SecurityContext, MDC de logs, EntityManager. Código que funciona perfectamente puede fallar solo por estar dentro de un assertTimeoutPreemptively, y el fallo no se parece en nada a un problema de tiempo.

El proyecto lo demuestra sin contarlo:

String hiloDelTest = Thread.currentThread().getName();

String hiloDeDentro = assertTimeoutPreemptively(Duration.ofSeconds(2),
        () -> Thread.currentThread().getName());

assertTrue(!hiloDelTest.equals(hiloDeDentro));   // pasa: son distintos

El mensaje de fallo, que es de lo mejor que da JUnit

Descomenta la línea marcada en TiempoTest.plazoImposible() — pide 120 ms de trabajo en 50 ms:

execution exceeded timeout of 50 ms by 91 ms
# el exceso exacto varia en cada maquina; el plazo, no

Te dice el plazo y por cuánto te pasaste. Con eso ya sabes si te falta afinar el código o mover la expectativa.

@Timeout: el plazo en la anotación

@Test
@Timeout(value = 3, unit = TimeUnit.SECONDS)
void plazoEnLaAnotacion() {
    assertNotNull(java101.actaDeInscripcion());
}

Cubre el método completo, no un bloque concreto. Se puede poner en la clase entera o en un @BeforeEach. En un servidor de integración, un @Timeout a nivel de clase es la red de seguridad barata contra el test que se cuelga y para el build. La versión global está en la sección 08.

La idea importante

03 Los tres estados

Hay tres, no dos. Y confundirlos es la causa número uno de suites que mienten.

PASSEDEl test corrió y la afirmación se cumplió.
FAILEDEl test corrió y la afirmación no se cumplió. Hay un bug.
ABORTEDEl test ni siquiera corrió. No se sabe nada.
assertTrue(false)   // -> FAILED   "esto esta mal"
assumeTrue(false)   // -> ABORTED  "aqui no aplica, ni lo intento"

Por qué importa la diferencia: un build con 300 tests abortados sale verde. Y verde, para quien lo mira de lejos, significa «todo probado». En este proyecto son 4 de 37 — mira otra vez el Skipped: 4 de la sección 00 y pregúntate qué rutas del código no se comprobaron.

Una assumption es un requisito del entorno

No es una afirmación sobre tu código. Se lee: «esto solo tiene sentido si…».

@Test
void soloEnElEntornoDeIntegracion() {
    assumeTrue("integracion".equals(System.getenv("ACADEMY_ENV")),
            "No estamos en el entorno de integracion: no aplica");

    // todo lo de abajo solo corre si la assumption se cumplio
}

assumingThat es otra cosa

Y casi nadie lo usa bien. La diferencia es de alcance:

Qué hace si la condición es falsa
assumeTrueAborta el test entero.
assumingThatSe salta solo ese bloque. El resto del test sigue corriendo.

Sirve para: «estas comprobaciones valen en todas partes; esta otra solo cuando estoy en la máquina de desarrollo».

@Disabled es deuda

@Test
@Disabled("2026-08-26 (mike): pendiente de la regla de lista de espera, ticket ACAD-142")
void listaDeEspera() { }

El texto no es opcional en la práctica. Es la única pista que tendrá quien lo encuentre dentro de seis meses — por eso lleva fecha, persona y ticket. Y la regla dura: un @Disabled es deuda, con fecha y con dueño. Si no piensas volver, borra el test; uno apagado para siempre solo sirve para inflar el número de tests del reporte.

Las condiciones declarativas

Mismo efecto que una assumption, pero a la vista en la firma en vez de escondidas en la primera línea del cuerpo.

@EnabledOnOs({ OS.MAC, OS.LINUX })
@EnabledIfSystemProperty(named = "academy.lento", matches = "true")
@EnabledIfEnvironmentVariable(named = "ACADEMY_ENV", matches = "integracion")

// existen tambien: @DisabledOnOs, @EnabledOnJre, @EnabledForJreRange,
// @DisabledIfSystemProperty y @EnabledIf (con un metodo propio)

Organizar

04 Agrupar por situación

El error común al organizar tests es hacer una clase por método: InscribirTest, CerrarTest, LugaresDisponiblesTest. Suena ordenado y no lo es — inscribir() se comporta de tres maneras distintas según cómo esté el curso, y en una sola clase esas tres se mezclan.

@Nested agrupa por situación. Cada clase interna monta un estado y ahí dentro prueba todo lo que aplica a ese estado.

CursoNestedTest.java — la estructura 
@DisplayName("Un curso")
class CursoNestedTest {

    private Curso curso;

    @BeforeEach                          // corre ANTES que el de dentro
    void crearCurso() { curso = new Curso("JAVA-101", 2); }

    @Nested
    @DisplayName("Cuando ya esta lleno")
    class Lleno {                          // NO puede ser static

        @BeforeEach                      // corre DESPUES del de fuera
        void llenarlo() {
            curso.inscribir("A01");        // 'curso' ya existe: lo monto el de fuera
            curso.inscribir("A02");
        }

        @Test @DisplayName("rechaza al siguiente con CupoLlenoException")
        void rechazaAlTercero() {
            assertThrows(CupoLlenoException.class, () -> curso.inscribir("A03"));
        }

        @Test @DisplayName("sigue abierto: lleno y cerrado no son lo mismo")
        void llenoNoEsCerrado() {
            assertTrue(curso.estaAbierto());
        }
    }
}

El resultado en el reporte se lee casi como una frase en español:

Un curso
  Cuando acaba de crearse
    ✓ tiene todos sus lugares libres
    ✓ acepta al primer inscrito
  Cuando ya esta lleno
    ✓ rechaza al siguiente con CupoLlenoException
    ✓ sigue abierto: lleno y cerrado no son lo mismo
  Cuando ya cerro inscripciones
    ✓ rechaza a cualquiera, aunque queden lugares
ojo Las clases internas NO pueden ser static@Nested necesita una instancia interna ligada a la externa — y es justo eso lo que hace que hereden el @BeforeEach de fuera. Si le pones static, JUnit deja de reconocerla y sus tests desaparecen del reporte sin error.

El beneficio que no se ve al principio. Fíjate en llenoNoEsCerrado: ese test solo tiene sentido dentro del grupo «cuando ya está lleno». En una clase plana, mezclado con otros veinte, nadie lo escribiría — no se le ocurre a nadie. La estructura no solo ordena los tests que ya tenías: te hace ver los que faltaban.

El experimento

05 Partir la suite en dos velocidades

El problema aparece solo, sin que nadie lo busque: la suite empieza en dos segundos, crece, y un día tarda once minutos. Entonces la gente deja de correrla antes de subir código. Y una suite que nadie corre no protege nada.

La salida no es tener menos tests: es poder correr una parte.

una corrida de ejemplo — tus segundos serán otros, la proporción no

Los tests con @Tag("lento") son 3 de 37 — un 8 % de la suite — y se llevan más de la mitad del tiempo de ejecución. Ese desequilibrio es la regla, no la excepción: en cualquier proyecto real un puñado de tests que tocan disco, red o base de datos acaba pesando más que los cientos que no tocan nada.

Un matiz honesto sobre esos números. Si cronometras las tres corridas con un reloj de pared vas a ver casi lo mismo (~2 s cada una): en un proyecto de este tamaño Maven tarda más en arrancar que en correr nada. Lo que compara el script es el tiempo que suma Surefire por clase — que es lo único que crece cuando tu suite crece.

El mecanismo

06 Lo que JUnit te inyecta

En la guía 01 dijimos que un test «no recibe parámetros». Era una mentira didáctica. La verdad es esta: JUnit resuelve los parámetros del método por tipo, igual que un contenedor de inyección de dependencias. Si pides un TestInfo, te lo da.

Y esto no es un truco cerrado. Es el mismo mecanismo — ParameterResolver — con el que Spring te inyecta el ApplicationContext en un @SpringBootTest. Entenderlo aquí, con tres clases y sin framework, hace que aquello se entienda solo. Funciona en @Test, en @BeforeEach, en @AfterEach y en el constructor.

PidesRecibesPara
TestInfoNombre del método, @DisplayName, clase y etiquetas del test que corre ahora.Logs que dicen qué test está a punto de correr.
TestReporterUn canal para publicar datos en el reporte, no en la consola.Dejar rastro atado al test que lo produjo.
@TempDir PathUn directorio real, vacío, que JUnit borra entero al terminar — pase o falle.Todo lo que escriba en disco.
RepetitionInfoQué repetición es esta. Ver guía 03.@RepeatedTest.
 
@Test
void variasALaVez(TestInfo info, TestReporter reporter, @TempDir Path carpeta)
        throws IOException {

    Path archivo = carpeta.resolve("evidencia.txt");
    Files.writeString(archivo, "test: " + info.getDisplayName());

    reporter.publishEntry("evidencia", archivo.getFileName().toString());

    assertTrue(Files.readString(archivo).contains("Varias inyecciones"));
}
// Los parametros van en cualquier orden: JUnit los resuelve por TIPO.

Por qué @TempDir merece la pena. Resuelve un problema viejo y feo: el test que escribe en /tmp/salida.txt, pasa la primera vez, y a la segunda pasa porque el archivo de la primera seguía ahí. Basura que sobrevive entre corridas y hace que la suite mienta. Con @TempDir eso no puede pasar — y no hay @AfterEach que mantener.

El aviso

07 El orden, y por qué es un error

Por defecto JUnit ejecuta los métodos en un orden determinista pero deliberadamente no obvio. No es un descuido de diseño: es una defensa. Si el orden fuera alfabético o el del archivo, se escribirían tests que dependen del anterior sin querer.

Y ya conoces la otra mitad de esa defensa: la instancia nueva por test de la guía 01. Entre las dos, JUnit te lo pone difícil a propósito.

Se pueden desactivar las dos:

OrdenTest.java 
@TestInstance(TestInstance.Lifecycle.PER_CLASS)   // una sola instancia:
@TestMethodOrder(MethodOrderer.OrderAnnotation.class)  // los campos sobreviven
class OrdenTest {

    private Curso curso;          // NO se reinicia entre tests

    @Test @Order(1) void seAbre()            { curso = new Curso("JAVA-101", 2); … }
    @Test @Order(2) void seLlena()           { curso.inscribir("A01"); … }
    @Test @Order(3) void noCabeUnTercero()   { … }
}

Lo que acabas de leer es una narración, no cuatro tests. Y tiene un precio que se paga el día que algo falla:

  • 1El test 3 no se puede correr solo En el IDE, ejecutar únicamente noCabeUnTercero truena con NullPointerException.
  • 2Un fallo se multiplica Si el test 1 falla, los otros tres fallan también. El reporte enseña cuatro rojos donde hay un problema.
  • 3Reordenar cambia el significado Nadie se atreve a tocarlo, y por tanto nadie lo mantiene.

Cuando de verdad quieras contar una secuencia, la forma sana es un solo test con los pasos dentro, o @Nested como en la sección 04.

El uso legítimo de PER_CLASS, que sí existe y es común: permite que @BeforeAll no sea static. Eso importa cuando el montaje caro — levantar un contenedor, abrir una conexión — necesita campos de instancia. Ahí PER_CLASS se usa por el @BeforeAll, no por compartir estado entre tests.

Y un MethodOrderer que sí vale la pena: Random. Revuelve el orden a propósito en cada corrida. Suena absurdo y es lo contrario: es la forma de cazar las dependencias ocultas entre tests antes de que te exploten en el servidor de integración.

Cierre

08 Suites y configuración global

@Suite: una selección con nombre

Una suite es una clase sin un solo @Test: solo dice qué ejecutar. Sirve para darle nombre a una selección que se repite.

SuiteDelCurso.java — la configuración ES la clase 
@Suite
@SuiteDisplayName("Humo: lo minimo que debe pasar antes de subir codigo")
@SelectClasses({ ExcepcionesTest.class, CursoNestedTest.class, EtiquetasTest.class })
@ExcludeTags("lento")
public class SuiteDelCurso { }
$ ./mvnw test -Dtest=SuiteDelCurso
[INFO] Tests run: 15, Failures: 0, Errors: 0, Skipped: 0

Necesita su propia dependencia, org.junit.platform:junit-platform-suite. Y ojo con Maven: el pom de este proyecto excluye la clase de mvn test. Si no, los tests que selecciona correrían dos veces — una por sí mismos y otra a través de la suite — y el conteo del reporte saldría inflado.

Nota honesta: con Maven las suites se usan poco, porque -Dgroups= sobre @Tag hace lo mismo sin clase extra ni exclusiones que mantener. Vale la pena conocerlas porque salen en código heredado.

junit-platform.properties

Un archivo en src/test/resources que JUnit lee solo. No hay que registrarlo en ninguna parte.

src/test/resources/junit-platform.properties 
# Nombres legibles sin escribir @DisplayName en cada metodo:
# convierte  void un_curso_lleno_rechaza()  en  "un curso lleno rechaza"
#junit.jupiter.displayname.generator.default = \
#    org.junit.jupiter.api.DisplayNameGenerator$ReplaceUnderscores

# Reparte los tests entre varios hilos. Ademas de bajar el tiempo,
# saca a la luz los tests que compartian estado sin saberlo.
#junit.jupiter.execution.parallel.enabled = true
#junit.jupiter.execution.parallel.mode.default = concurrent

# Red de seguridad contra el test que se cuelga y para el build:
junit.jupiter.execution.timeout.testable.method.default = 30 s

En el proyecto casi todo está comentado a propósito: descomenta y corre mvn test para ver el efecto. La única activa es el timeout global.

09 Trampas y ejercicios

Ejercicios

  • 1El mensaje frágil Escribe un test que afirme sobre ex.getMessage() con un assertEquals exacto. Ahora cambia una palabra del mensaje en CupoLlenoException. Se rompió un test sin que nada esté mal: eso es un test frágil.
  • 2La cuarta situación Añade a CursoNestedTest un @Nested para «cuando está lleno Y cerrado». ¿Qué excepción gana? Descúbrelo con un test, no leyendo el código.
  • 3Etiqueta lo tuyo Marca @Tag("integracion") la clase InyeccionTest entera y comprueba que -DexcludedGroups=integracion la salta completa.
  • 4Caza una dependencia oculta Cambia el MethodOrderer de OrdenTest por MethodOrderer.Random.class y corre varias veces. Explica exactamente por qué falla.
  • 5Assumption contra @Disabled Convierte el @Disabled de listaDeEspera en un assumeTrue(false). ¿Cambia algo en el reporte? ¿Cuál de los dos comunica mejor la intención?
  • 6Paralelismo Descomenta las dos líneas de paralelismo en junit-platform.properties y corre la suite varias veces. Si algo empieza a fallar de forma intermitente, acabas de encontrar un test que compartía estado.
